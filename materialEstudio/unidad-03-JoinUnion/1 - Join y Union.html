Unidad 3 · JOINS · MySQL 8

Consultar información que está repartida en varias tablas

Hasta ahora una consulta podía recuperar y filtrar filas de una tabla. Pero una base relacional distribuye la información para evitar repeticiones. Los JOINs permiten volver a reunir, al consultar, los datos que el diseño separó correctamente.

INNER JOINLEFT JOINRIGHT JOINVarias tablas

Al terminar esta unidad

  • Comprender para qué sirve un JOIN y qué papel cumple la condición ON.
  • Distinguir qué filas conserva INNER JOIN, LEFT JOIN y RIGHT JOIN.
  • Combinar progresivamente más de dos tablas usando alias claros.
  • Interpretar los NULL que aparecen cuando no existe una coincidencia.
  • Evitar productos cartesianos accidentales y reconocer la diferencia entre JOIN y UNION.
01 · El problema que resuelve JOIN

Los datos están separados… y eso está bien

Tomemos el mismo ejemplo sencillo del material histórico de la materia: productos y categorías. En un diseño normalizado no repetimos el nombre de la categoría en cada producto. Guardamos la categoría una sola vez y la relacionamos mediante una clave foránea.

Si queremos mostrar “Laptop — Tecnología” o “Yerba — Alimento”, necesitamos leer columnas de las dos tablas en una misma consulta.

La idea central: un JOIN no vuelve a guardar los datos juntos. Los combina solamente para producir el resultado de una consulta.
02 · Anatomía básica

¿Cómo se escribe un JOIN?

productos ptabla de la izquierda
↔p.id_categoria = c.id_categoria
categorias ctabla de la derecha
SELECT
    p.nombre,
    c.nombre_categoria
FROM productos AS p
INNER JOIN categorias AS c
    ON p.id_categoria = c.id_categoria;

ON expresa el criterio que relaciona las filas. En este curso, la situación más habitual será unir una FK con la PK que referencia.

Alias: p y c hacen la consulta más corta y permiten indicar sin ambigüedad de qué tabla sale cada columna.

En MySQL, escribir solamente JOIN sin indicar el tipo equivale a INNER JOIN. En el material usaremos el nombre completo al principio porque deja más claro qué operación estamos realizando.

03 · Solo las coincidencias

INNER JOIN

INNER JOIN conserva únicamente las filas para las que existe coincidencia entre ambas tablas según la condición indicada en ON.

Izquierda

Se consideran los productos.

Solo si coinciden

Coincidencia

productos.id_categoria = categorias.id_categoria

Es el criterio

Derecha

Se consideran las categorías.

Solo si coinciden
SELECT
    p.id_producto,
    p.nombre,
    c.nombre_categoria
FROM productos AS p
INNER JOIN categorias AS c
    ON p.id_categoria = c.id_categoria;

El producto Termómetro no aparece porque no tiene categoría asociada. La categoría Limpieza tampoco aparece porque ningún producto está relacionado con ella.

04 · Conservar todo lo de la izquierda

LEFT JOIN

LEFT JOIN conserva todas las filas de la tabla escrita a la izquierda. Cuando existe coincidencia, agrega los datos de la tabla derecha; cuando no existe, esas columnas aparecen como NULL.

SELECT
    p.id_producto,
    p.nombre,
    c.nombre_categoria
FROM productos AS p
LEFT JOIN categorias AS c
    ON p.id_categoria = c.id_categoria;
id_productonombrenombre_categoria
1LaptopTecnología
2YerbaAlimento
3TermómetroNULL
Pregunta que responde: “Quiero ver todos los productos, incluso aquellos que todavía no tengan una categoría asociada”.
05 · Conservar todo lo de la derecha

RIGHT JOIN

RIGHT JOIN hace la idea inversa: conserva todas las filas de la tabla escrita a la derecha, aunque no exista coincidencia en la izquierda.

SELECT
    p.nombre,
    c.id_categoria,
    c.nombre_categoria
FROM productos AS p
RIGHT JOIN categorias AS c
    ON p.id_categoria = c.id_categoria;
nombreid_categorianombre_categoria
Yerba1Alimento
Laptop2Tecnología
NULL3Limpieza

Ahora aparece Limpieza, aunque no tenga productos. En cambio, Termómetro no aparece porque la consulta decidió conservar todas las categorías, no todos los productos.

Dato práctico: muchas consultas con RIGHT JOIN pueden reescribirse como LEFT JOIN invirtiendo el orden de las tablas. Conviene elegir la forma que haga más clara la intención de la consulta.
06 · Una forma abreviada cuando la columna se llama igual

USING como alternativa sencilla a ON

Después de comprender la forma general de un JOIN con ON, MySQL ofrece una escritura más corta para algunos casos: USING.

Puede utilizarse cuando las dos tablas se relacionan mediante una columna que tiene el mismo nombre en ambas tablas.

Forma general con ON

SELECT
    p.nombre,
    c.nombre_categoria
FROM productos AS p
INNER JOIN categorias AS c
    ON p.id_categoria = c.id_categoria;

La misma relación con USING

SELECT
    p.nombre,
    c.nombre_categoria
FROM productos AS p
INNER JOIN categorias AS c
    USING (id_categoria);

En ambos casos la intención es la misma: relacionar productos con categorías mediante id_categoria. Con USING no se escriben los nombres de las dos tablas dentro de la condición porque MySQL ya sabe que debe buscar esa columna en ambas.

Regla fácil: si la columna de relación se llama igual en las dos tablas, USING (columna) puede simplificar la consulta.
No reemplaza a ON: ON es más general y flexible. Si las columnas tienen nombres diferentes o la condición de unión es más compleja, debe utilizarse ON.

Por ejemplo, esto no podría expresarse directamente con USING si una tabla tuviera id_categoria y la otra categoria_id:

... JOIN categorias AS c
    ON p.categoria_id = c.id_categoria;

USING también puede utilizarse con otros tipos de JOIN, como LEFT JOIN, siempre que la columna indicada exista con el mismo nombre en ambas tablas.

Criterio de la cátedra: aprender primero ON porque permite comprender explícitamente qué columnas se relacionan. Después, utilizar USING como una abreviatura cómoda cuando el caso sea simple y claro.
07 · Una relación detrás de otra

Combinar más de dos tablas

Una consulta puede encadenar varios JOINs. La clave es pensar cada unión por separado y escribir con claridad qué columnas relacionan cada par de tablas.

Supongamos que cada producto también tiene un proveedor:

SELECT
    p.nombre AS producto,
    c.nombre_categoria AS categoria,
    pr.nombre_proveedor AS proveedor
FROM productos AS p
INNER JOIN categorias AS c
    ON p.id_categoria = c.id_categoria
INNER JOIN proveedores AS pr
    ON p.id_proveedor = pr.id_proveedor;
Estrategia: leer la consulta de a pares: productos con categorías; luego, el resultado se relaciona con proveedores. No hace falta intentar imaginar todas las tablas al mismo tiempo.

Los alias se vuelven especialmente importantes cuando varias tablas poseen columnas con nombres iguales, como id_categoria, nombre o fecha.

08 · Aprovechar los NULL del resultado

Detectar filas sin correspondencia

Los JOINs externos no solo sirven para “mostrar todo”. También permiten encontrar qué filas no poseen una relación.

Por ejemplo, para buscar productos sin categoría asociada:

SELECT
    p.id_producto,
    p.nombre
FROM productos AS p
LEFT JOIN categorias AS c
    ON p.id_categoria = c.id_categoria
WHERE c.id_categoria IS NULL;

Primero el LEFT JOIN conserva todos los productos. Para los que no encuentran categoría, las columnas de c quedan en NULL. Luego WHERE c.id_categoria IS NULL se queda únicamente con esos casos.

No confundir: ese NULL puede indicar que la tabla derecha no tuvo coincidencia. No significa necesariamente que el dato original de la tabla izquierda estuviera guardado como NULL.
09 · Un error muy común

Evitar productos cartesianos accidentales

Si combinamos tablas sin indicar correctamente cómo se relacionan, podemos obtener todas las combinaciones posibles entre sus filas.

Ejemplo problemático: 3 productos × 3 categorías pueden producir 9 combinaciones, aunque muchas no tengan ningún sentido para el negocio.
-- Falta el criterio que relaciona ambas tablas
SELECT
    p.nombre,
    c.nombre_categoria
FROM productos AS p,
     categorias AS c;

La solución no es “arreglar el resultado después”, sino expresar correctamente la relación mediante JOIN ... ON ....

Regla práctica: cada vez que agregues una tabla a una consulta, preguntate: “¿con qué tabla se relaciona y mediante qué columnas?”.
10 · Dos ideas distintas

JOIN no es lo mismo que UNION

JOIN → combina columnasRelaciona filas de tablas distintas y arma un resultado “más ancho”.
vs.
UNION → combina filasApila resultados compatibles y arma un resultado “más largo”.

Por ejemplo, si tenemos dos consultas que devuelven nombre y email, podemos reunir ambas listas:

SELECT nombre, email
FROM clientes
UNION
SELECT nombre, email
FROM proveedores;

Para usar UNION, ambas consultas deben devolver la misma cantidad de columnas y posiciones con tipos compatibles. UNION elimina filas duplicadas; UNION ALL las conserva.

Ejemplo práctico: reunir depósitos y extracciones como movimientos

Supongamos que un sistema bancario guarda los depósitos y las extracciones en tablas diferentes. Si queremos mostrar un único listado cronológico de movimientos, no necesitamos relacionar una fila de una tabla con una fila de la otra: necesitamos apilar ambos resultados.

Tabla depósitos

id_deposito, id_cuenta, fecha, monto

Tabla extracciones

id_extraccion, id_cuenta, fecha, monto

SELECT
    fecha,
    id_cuenta,
    'Depósito' AS tipo,
    monto
FROM depositos

UNION ALL

SELECT
    fecha,
    id_cuenta,
    'Extracción' AS tipo,
    monto
FROM extracciones

ORDER BY fecha, id_cuenta;
fechaid_cuentatipomonto
2026-08-1012Depósito50000
2026-08-1112Extracción12000
2026-08-127Depósito30000

El resultado puede leerse como un único listado de movimientos, aunque físicamente los datos sigan almacenados en dos tablas distintas. Las dos consultas devuelven cuatro columnas compatibles y en el mismo orden.

¿Por qué UNION ALL en este caso? Dos operaciones reales podrían tener exactamente la misma fecha, cuenta, tipo y monto. UNION podría eliminar una fila por considerarla duplicada; UNION ALL conserva todos los movimientos.
Para no mezclar conceptos: usamos JOIN cuando queremos relacionar tablas; usamos UNION cuando queremos juntar resultados compatibles uno debajo del otro.
11 · Escribir consultas claras

Criterios prácticos para trabajar con JOINs

  • Identificar primero qué información se necesita y en qué tablas se encuentra.
  • Reconocer las PK y FK que expresan las relaciones del modelo.
  • Usar alias breves y consistentes: p, c, pr, etc.
  • Calificar las columnas cuando puede existir ambigüedad: p.nombre, c.nombre.
  • Elegir INNER, LEFT o RIGHT según qué filas deban conservarse, no por costumbre.
  • Evitar SELECT * en consultas reales cuando solo se necesitan algunas columnas.
  • Relacionar normalmente mediante columnas clave e índices adecuados; las PK ya están indexadas y las relaciones bien diseñadas ayudan al motor a resolver la consulta.
  • Comprobar el resultado paso a paso cuando se agregan varias tablas.
Sobre rendimiento: en esta unidad alcanza con una idea básica: unir solo las tablas necesarias, usar condiciones de relación correctas y trabajar con claves apropiadas. El optimizador de MySQL decidirá el plan físico de ejecución; no debemos inventarlo mirando únicamente el orden en que escribimos los JOINs.
